# 09. Диагностика и идентификация: обратная задача

Файл фиксирует результаты анализа расчётного ядра `v1` и проектное решение по
переходу от поверочного (прямого) расчёта к **диагностике деградации узлов**
турбоустановки: КПД отсеков турбины, КПД (загрязнение) подогревателей,
неплотности арматуры, трубные протечки.

> Статус: проектный документ. Код `v1` на момент написания не изменялся; все
> приведённые числа получены запуском текущего расчётного ядра и `WaterSteam`
> (IF97 2.0.0) при параметрах демонстрационной схемы
> (`p0 = 24 МПа`, `t0 = 540 °C`, `p1 = 3.5`, `p2 = 0.6`, `p3 = 0.12`,
> `p_к = 0.004 МПа`, `η_oi = 0.85`, `δt = 5 K`).

## 9.1. Прямая и обратная задача

Исходная точка — работоспособный прототип `v1` (`RegenerativeCycle`,
`EquationSystem`, `OjAlgoSolver`, `FixedFlow`): квадратная система 7×7 для схемы
ПВД + деаэратор + ПНД + конденсатор, 12 модульных тестов.

| | Прямая задача (v1) | Обратная задача (диагностика) |
|---|---|---|
| Что задано | все давления, температуры, КПД, недогревы, расход `G0` | часть расходов/температур с датчиков, часть — неизвестные |
| Что ищем | расходы отборов и мощность | отклонения параметров узлов (η, протечки) |
| Математика | квадратная СЛАУ `A·x = b`, один `LU` | переопределённая/недоопределённая система, минимизация невязки |
| Число решений | одно | семейство; нужны регуляризация и оценка идентифицируемости |

Ключевая мысль: **диагностика — это не «дорешать недоопределённую схему»,
а оценить параметры модели по измерениям.** Поэтому `FixedFlow` в схеме — это
фактически «недостающий датчик расхода», а не вычислительный трюк.

## 9.2. Почему квадратной системы недостаточно

### 9.2.1. Недоопределённая система

`EquationSystem.solve()` отвергает неквадратную систему ещё до вызова
решателя, поэтому «просто убрать одно измерение» нельзя: математически
получается бесконечное аффинное семейство решений.

Для балансовой части схемы система **однородна** по расходам (`A·x = 0`):
все уравнения — линейные комбинации произведений `G·h`, т.е. масштабируются.
Отсюда

```
A·x = 0  ⇒  x = t·x_ref,  t > 0   (любой масштаб — решение)
```

Схема **масштабно-инвариантна**: расходы отборов, мощность, теплоты котла и
конденсатора умножаются на `t` без нарушения балансов. Абсолютный масштаб
задаётся только внешним ограничением — расходом свежего пара `G0`
(`FixedFlow`).

### 9.2.2. Поведение ojAlgo (проверено на 57.4.0)

| Инструмент | Поведение на вырожденной системе |
|---|---|
| `LU.R064.decompose()` | возвращает `true` **даже для сингулярной матрицы** |
| `LU.isSolvable()` | `false` — корректный признак несовместности |
| `LU.solve()` | `Optional.empty()` |
| `QR` | `isSolvable() = false` |
| `SVD` | решение минимальной нормы: для `A·x = 0` это тривиальный `x = 0`, для неоднородной — проекция без физического смысла |

Вывод: **минимизация нормы не является физически осмысленным способом
«дорешать» схему** — она ломает структуру потоков (например, делает все отборы
одинаково малыми), а не восстанавливает реальный режим.

### 9.2.3. LP/MILP: что можно и что нельзя

`ojAlgo` 57.4.0 содержит решатели LP/MILP, т.е. новая зависимость не нужна.
Но на **однородных** балансах любая линейная цель вырождена:

- `max c·x` → неограниченно (масштаб `t` можно увеличивать);
- `min c·x` → вырожденный нуль.

Следовательно, **масштаб потоков оптимизацией не определяется**. LP/MILP
действительно полезны для другого:

- интервальные оценки параметров `θ` при фиксированной нагрузке (min/max);
- разреженная локализация неисправностей (`Σz_i ≤ k`, big-M);
- дробно-линейная задача `max η` (преобразование Чарнса–Купера).

## 9.3. Идентифицируемость определяется составом измерений

Число независимо оцениваемых параметров равно **рангу якобиана
чувствительностей**, а не разности «уравнения минус неизвестные»:

```
θ ∈ R^p,  J = ∂r/∂θ ∈ R^(m×p),  rank(J) = число идентифицируемых параметров
```

Практические следствия, важные для проекта:

1. Если в камерах отбора нет термометров, четыре КПД отсеков турбины
   **схлопываются в один агрегатный** `η_oi` (ранг 1) — разделить их по
   расходам и мощностям невозможно.
2. В области влажного пара температура **не является независимым измерением**:
   `T = T_sat(p)`. Для демонстрационной схемы это критично: проверка по IF97
   даёт `x(p2 = 0.6 МПа) = 0.931`, `x(p3 = 0.12 МПа) = 0.871`, поэтому
   температура в этих отборах не несёт информации о состоянии пара.
3. Отчёт о диагностике обязан различать «параметр оценён» и «параметр
   неидентифицируем»; последнее — результат, а не ошибка.

## 9.4. Найденные дефекты v1

### 9.4.1. Проверка совместности в `OjAlgoSolver`

Ветка `if (!lu.decompose(...))` **никогда не срабатывает**: ojAlgo возвращает
`true` даже для сингулярной матрицы. Реальная диагностика — `isSolvable()`:

```java
// было: ветка недостижима
if (!lu.decompose(matrix)) {
    throw new IllegalStateException("LU decomposition failed");
}
// стало:
lu.decompose(matrix);
if (!lu.isSolvable()) {
    throw new IllegalStateException("система вырождена: rank(A) < n");
}
```

### 9.4.2. Сводка дефектов

| Место | Симптом | Причина | Решение |
|---|---|---|---|
| `OjAlgoSolver` | сообщение о вырожденности не выдаётся | `decompose()` не проверяет сингулярность | явный `isSolvable()` |
| `EquationSystem` | нет способа проверить качество решения | нет невязки | `residual(double[])` + тест `‖A·x − b‖∞ ≤ 1e-9` |
| `EquationSystem.solve` | непонятная ошибка на неквадратной системе | проверка размерности до решателя | сообщение с размерами и подсказкой про `FixedFlow` |

## 9.5. Трубная неплотность (протечка) в поверхностном подогревателе

### 9.5.1. Почему текущая модель её не описывает

`SurfaceHeater` **отождествляет** переменные: вход воды = выход воды
(`feedwater`), а расход дренажа = расход отбора. Это тождество, а не уравнение,
поэтому протечка структурно невозможна — нет переменной `G_ут`.

### 9.5.2. Обобщённая модель: три уравнения

```
1) вода:    G_wi = G_wo + G_ут
2) дренаж:  G_д  = G_с  + G_ут
3) энергия: G_с·h_с + G_wi·h_wi = G_д·h_д + G_wo·h_wo
```

Подстановка (1)–(2) в (3):

```
G_с·(h_с − h_д) = G_wi·(h_wo − h_wi) + G_ут·(h_д − h_wo)
```

При `G_ут = 0` получается в точности текущее уравнение, а тепловой член утечки
равен `h_д − h_wo = h′ − (h′ − c_p·δt) = c_p·δt`.

### 9.5.3. Сигнатура неисправности

| Канал | Эффект при `G_ут > 0` | Оценка для ПВД |
|---|---|---|
| Масса | `G_wo = G_wi − G_ут`, `G_д = G_с + G_ут` | **точный, 100 % сигнала** |
| Энергия | слагаемое `G_ут·(h_д − h_wo)` | `c_p·δt = 4.77·5 = 23.8` кДж/кг ≈ 7 % от теплоты ПВД (323 кДж/кг) |
| Отбор ПВД | растёт (греется «лишняя» вода) | **+0.07 %** на 1 % утечки — слабо |
| Дренаж | больше горячего дренажа в деаэратор → мощность цикла чуть растёт | малый, положительный |

Вывод: тепловой канал протечки **маскируется под загрязнение** (растёт отбор при
той же температуре питательной воды), а мощность при этом даже слегка растёт.
Поэтому протечка **идентифицируема только по расходам**; без расходомеров на
входе/выходе подогревателя она должна попадать в отчёт как
«неидентифицируема», а не как «η = 0.97».

### 9.5.4. Размерность системы после обобщения

Разделение `feedwater` на вход/выход ПВД, `condensate` на вход/выход ПНД и
отдельные `hpDrain`/`lpDrain` дают **11 неизвестных вместо 7**; система остаётся
квадратной (11×11), решатель не меняется. `leakFlow` — параметр (`double`), а не
неизвестная: он задаётся гипотезой или оценивается внешним слоем.

## 9.6. Трёхзонная модель поверхностного подогревателя (ОП + К + ОД)

### 9.6.1. Зоны и их уравнения

Вода движется противотоком: ОД → К → ОП.

| Зона | Пар / конденсат | Вода | Теплота на 1 кг отбора |
|---|---|---|---|
| **ОП** — охлаждение перегрева | `h_с → h″(p)` | `h_b → h_wo` | `h_с − h″` |
| **К** — конденсация | `h″ → h′` | `h_a → h_b` | `h″ − h′` |
| **ОД** — охлаждение дренажа | `h′ → h_др.вых` | `h_wi → h_a` | `h′ − h_др.вых` |

```
ОП: G_с·(h_с − h″)      = G_w·(h_wo − h_b)
К:  G_с·(h″ − h′)       = G_w·(h_b − h_a)
ОД: G_с·(h′ − h_др.вых) = G_w·(h_a − h_wi)
```

Сумма трёх уравнений даёт общий тепловой баланс подогревателя — значит
**зональные уравнения не добавляют новой физики, а лишь перераспределяют
теплоту**.

### 9.6.2. Что влияет на балансы схемы, а что нет

Оценка для ПВД (`p1 = 3.5 МПа`, проверено по IF97):

| Зона | Теплота на 1 кг отбора, кДж/кг | Доля | Влияние на балансы схемы |
|---|---|---|---|
| ОП (`h1 = 2901.258 → h″ = 2802.744`) | 98.515 | **5.32 %** | **нет**: полный перепад `h_с → h′` уже в одном уравнении |
| К (`h″ → h′ = 1049.775`) | 1752.969 | 94.68 % | «ядро» текущей модели |
| ОД (`h′ → h_др.вых`) | зависит от TTD | — | **да**: меняет `h_др` в балансе подогревателя и деаэратора |

Итого теплота ПВД `Q = 323.252` кДж/кг (совпадает с демо:
`G1·(h1 − h′) = 0.174591·1851.483`).

**Правило:** ОП и К не меняют ни расход отбора, ни мощность — они
перераспределяют уже учтённую теплоту. Меняет балансы только ОД, потому что
задаёт энтальпию дренажа на выходе, а она входит в уравнение следующего узла.

### 9.6.3. Счёт неизвестных и уравнений

**Вариант «зоны как неизвестные СЛАУ»:**

| | Количество |
|---|---|
| Неизвестные | `G_с`, `h_др.вых`, `h_a`, `h_b` = **4** |
| Уравнения | 3 зональных баланса = **3** |
| Итог | недоопределено на **1** — не хватает условия TTD дренажного охладителя |

**Вариант «`h_др.вых` задан» (TTD ОД или измерение):**

| | Количество |
|---|---|
| Неизвестные | `G_с`, `h_a`, `h_b` = **3** |
| Уравнения | 3 |
| Итог | квадратная; при этом `h_a`, `h_b` считаются **явно** (пост-обработка) |

Вывод: **«зон больше → уравнений больше» верно только как «неизвестных и
уравнений больше на одно и то же число»**. Степень свободы схемы и размер
СЛАУ (11×11 в обобщённой модели) не меняются.

### 9.6.4. Автоопределение числа зон по параметрам пара

```
ОП:  Δh_ОП = h_с − h″(p_отб)        Δh_ОП > 0  ⇒  зона есть
                                    Δh_ОП ≤ 0  ⇒  пар влажный, зоны нет
ОД:  h_др.вых = h′(p_отб)           дренажного охладителя нет
     h_др.вых < h′(p_отб)           охладитель есть (задаётся TTD)
недогрев: h_wo = h′(p_отб) − c_p·δt  (как в текущей модели)
```

Проверка на демонстрационной схеме:

| Узел | `p`, МПа | `h_с` | `h″(p)` | `h_с − h″` | `x` | ОП | Всего зон |
|---|---|---|---|---|---|---|---|
| ПВД | 3.5 | 2901.258 | 2802.744 | **+98.515** | перегрет (`T = 272.500 °C`) | **есть** | **3** (ОП+К+ОД)* |
| ПНД | 0.12 | 2393.240 | 2683.058 | **−289.818** | **0.871** | **нет** | **2** (К+ОД) |
| Деаэратор | 0.6 | 2613.131 | — | — | **0.931** | нет | смеситель (зон нет) |

\* при наличии дренажного охладителя в проекте; иначе 2 (ОП+К).

Формально признак «пар перегрет» — `h_с > h″(p)`; в коде проверять именно это,
а не `NaN` от `vapourFractionPH` (для перегретого пара метод действительно
возвращает `NaN`, но опираться на это хрупко).

Та же проверка автоматически ловит **исчезновение ОП-зоны в нерасчётном
режиме** — это самостоятельный диагностический признак (пар на входе стал
влажным = проблема в предыдущем отсеке или сепараторе).

### 9.6.6. Почему это критично именно для диагностики

Смещение предсказанных отборов на 12–14 % на порядок больше любой реальной
неисправности (загрязнение подогревателя даёт единицы процентов). Если ОД не
учитывать, метод невязок будет устойчиво показывать «неисправность» на
**здоровой** схеме, и никакой порог это не исправит. Для КПД цикла поправка
умеренная (часть эффекта компенсируется ростом отбора на деаэратор), но для
диагностики она обязательна.

### 9.6.7. Нелинейность условий TTD

Условие TTD — это `T(h)`, т.е. **нелинейно**. Отсюда практическое правило:

| Режим | Как обращаться с `h_др.вых` | Последствия |
|---|---|---|
| Проектный / номинальный | `h_др.вых = enthalpyPT(p, T_wi + Δt_ОД)` считается **до** сборки СЛАУ | система остаётся линейной 11×11 |
| Диагностика | `T_др.вых` — измерение | новых неизвестных нет |
| Поиск `h_др.вых` как неизвестной | появляется нелинейное уравнение TTD | нужна внешняя итерация; в линейную СЛАУ не вносить |

Валидация обязательна: `h_др.вых > h_wi` (иначе ОД не отдаёт теплоту),
`T_wo ≤ T_с − Δt_ОП.min`, `h_a, h_b ∈ [h_wi, h_wo]`.

### 9.6.8. Что зоны дают диагностике

| Что деградировало | Как меняется модель | Наблюдаемая сигнатура | Чем идентифицируется |
|---|---|---|---|
| ОП (загрязнение) | `Q_ОП ↓` | `T_пв ↓` вплоть до **3.66 K** (`237.54 → 233.90 °C`) | `T_пв` |
| К (загрязнение) | `Q_К ↓` | `T_пв ↓` **и** `G_с ↑` одновременно | `T_пв` + `G_с` |
| ОД (загрязнение, завоздушивание) | `h_др.вых → h′` | `T_др ↑` | `T_др` |
| Отсек турбины | `η_oi ↓` | `G_отб ↑`, `N ↓` | нужны `T`/`p` камеры отбора |
| Трубная протечка | `G_ут > 0` | расходы воды изменяются точно, `T_пв` — слабо | **только** `G_wi`, `G_wo` |
| Неплотность арматуры | переток между узлами | расход и энтальпия смеси | расходы или `T` смеси |

Дополнительно:

1. Зоны **разделяют** один слипшийся КПД на три, причём с разными направлениями
   в пространстве измерений (см. таблицу) — это именно то, чего не хватало
   КПД отсеков турбины (там ранг был 1).
2. `T_др.вых` — новая полноценная наблюдаемая величина.
3. Модель **ортогональна** модели протечки: уравнения массы не меняются, поэтому
   `G_ут` остаётся чисто массовой сигнатурой.
4. Число активных зон — **детерминированная функция состояния на входе**, но при
   нерасчётных режимах её можно рассматривать как дискретную гипотезу
   ({ОП есть / нет}, {ОД есть / нет}) для перебора в диагностике.

Ограничение (честно): измерений `T_пв` и `T_др` всего два, поэтому из трёх
зональных КПД идентифицируемы максимум два; ранг якобиана это покажет, и отчёт
должен выдать третий как «неидентифицируем».

### 9.6.9. Риски и ограничения

- Зоны **не описывают** гидравлику, уровень в корпусе и байпасирование — при
  больших перегрузках профиль недостоверен.
- Граница ОП/К определяется **состоянием** (достижением насыщения), а не
  поверхностью, поэтому зональные теплоты полностью определены энтальпиями;
  поверхностно-ограничен **только** выход ОД.
- Не следует вносить зоны в СЛАУ как отдельные неизвестные: размер растёт,
  добавляется нелинейность, а точность балансов не меняется.

## 9.7. Предлагаемая архитектура

```
PlantState (номинал + отклонения)
        │
        ▼
RegenerativeCycle.calculate(state)   ← детерминированный внутренний расчёт (LU, мс)
        │ прогноз
        ▼
MeasurementSet ──► невязки ──► Estimator (LM + Tikhonov) ──► DiagnosisReport
                                    ▲                              ▲
                          Jacobian (числ. производные)     Identifiability (SVD)
```

| Класс | Ответственность |
|---|---|
| `PlantState` | номинальный `CycleDesign` + отклонения (КПД отсеков, зональные КПД, протечки) |
| `MeasurementSet` | какие величины измеряются, их значения и погрешности |
| `Jacobian` | численные производные невязок по параметрам |
| `Identifiability` | SVD якобиана, ранг, перечень идентифицируемых/неидентифицируемых параметров |
| `Estimator` | Левенберг–Марквардт с тихоновским приором |
| `DiagnosisReport` | оценки, интервалы, невязки по узлам, предупреждения |
| `SyntheticPlant` | эталонный расчёт + шум → тесты «заложил неисправность — нашёл» |
| `HeaterZones` | автоопределение зон подогревателя по состоянию пара (чистая функция) |

Инварианты, которые обязаны сохраняться:

- при `leakFlow = 0`, `η = 1` и `h_др.вых = h′` результаты совпадают с текущим
  демо **до 1e-12**;
- глобальный баланс `Q_котла + N_насоса = N_турб + Q_конд` закрывается точно при
  любых протечках (утечка — внутренняя рециркуляция, а не потеря).

## 9.8. Порядок внедрения

1. **Мелкое и безопасное:** `EquationSystem.residual(double[])`, явный
   `lu.isSolvable()` с точным сообщением, тест `‖A·x − b‖∞ ≤ 1e-9`. Существующие
   12 тестов не затрагиваются.
2. **`SurfaceHeater`:** параметры `efficiency` (дефолт `1.0`), `leakFlow` (дефолт
   `0.0`), `drainOutletEnthalpy` (дефолт `h′`), метод `zoneProfile(...)`; новый
   `HeaterZones.of(...)`.
3. **`RegenerativeCycle`:** переход к 11×11, разделение вход/выход воды ПВД и ПНД,
   отдельные дренажи ПВД/ПНД, расширение `CycleResult` зональным отчётом;
   `PlantState`.
4. **Идентифицируемость:** `MeasurementSet`, `Jacobian`, `Identifiability` (SVD) →
   первый отчёт о ранге и о том, какие параметры различимы при данном наборе
   датчиков.
5. **Оценивание:** `Estimator` (Левенберг–Марквардт + тихоновский приор),
   `DiagnosisReport`.
6. **Проверка на синтетике:** `SyntheticPlant` — заложить неисправность, убедиться,
   что оценщик её находит, а неидентифицируемое возвращает как «нет данных».
7. **Опционально:** LP/MILP — интервальные оценки и разреженная локализация
   (`Σz_i ≤ k`, big-M).

Порядок важен: пункты 1–3 дают точную прямую модель (без неё оценщик бессмыслен),
пункт 4 отвечает на вопрос «что вообще можно узнать», и только потом имеет смысл
пункт 5.
